# Серверная часть

Go 1.27.4 или новее, PostgreSQL, MongoDB 8.0 и ClamAV для загрузки вложений. Исходники Go находятся в `cmd` и `internal`, схема — в `migrations`. Секреты никогда не добавлять в `frontend` или `VITE_*`.

Текущее окружение сессии, 19.11.2026: `backend/.env` настроен на облачную Supabase (Oregon, us-west-2) и MongoDB Atlas (AWS N. Virginia, us-east-1). Миграция и первоначальные вымышленные данные применены. Файл исключён из Git; учётные данные приложения находятся в его полях DEMO_*. Локальный Go API использует эти облачные базы. Временные базы прошлого этапа больше не являются источником данных запущенного API.

## Локальный запуск

1. Подготовить отдельную PostgreSQL и MongoDB. Для PostgreSQL создать пустую базу, например `mgimo_local`, доступную вашему локальному пользователю.
2. Скопировать `backend/.env.example` в `backend/.env`, заменить строку PostgreSQL, MongoDB URI и JWT_SECRET. Пример предназначен для localhost; пароль-заглушка не используется автоматически.
3. Из папки `backend` загрузить переменные окружения и применить миграции:

```sh
set -a
source .env
set +a
go run ./cmd/manage migrate
```

Для публичного PostgreSQL использовать TLS с проверкой сертификата (`sslmode=verify-full`, при необходимости `sslrootcert`). Для миграций нужен прямой адрес либо session pooler: блокировка обслуживания привязана к физической сессии. Сервер использует небольшой пул и режим pgx без кешируемых prepared statements; он совместим с transaction pooler. Доступ браузера через `anon`/`authenticated` к учебным таблицам закрыт. Go должен подключаться от серверной роли с нужными разрешениями и обходом RLS, например владельца отдельной базы прототипа. Не подключать браузер от этой роли.

Демонстрационные данные добавляются только явно:

```sh
export ALLOW_DEMO_SEED=true
read -s 'DEMO_PASSWORD?Пароль демонстрационных аккаунтов, минимум 12 символов: '
export DEMO_PASSWORD
go run ./cmd/manage seed
unset ALLOW_DEMO_SEED
go run ./cmd/server
```

Команда `read` выше предназначена для zsh. Seed создаёт только вымышленные данные и не перезаписывает существующие строки. Повторный seed не меняет пароли уже созданных аккаунтов. Для смены пароля нужен отдельный согласованный процесс, а не повторное заполнение базы.

| Email | Роль |
| --- | --- |
| student1@example.test | STUDENT, группа 101 |
| student2@example.test | STUDENT, группа 102 |
| teacher@example.test | TEACHER |
| support@example.test | SUPPORT |
| dean@example.test | DEAN |
| admin@example.test | ADMIN |

Пароль у этих аккаунтов — выбранный при первом seed `DEMO_PASSWORD`. Фиксированного встроенного пароля входа нет. Сервер: `127.0.0.1:8080`. Во втором терминале из корня репозитория:

```sh
npm ci
npm run dev
```

Открывать `http://localhost:5173`: он должен точно совпадать с `APP_ORIGIN`. Другой порт или имя хоста требуют изменения `APP_ORIGIN`. Vite проксирует API; передача refresh cookie проверена через этот прокси. В публичном окружении установить `COOKIE_SECURE=true`, `APP_ORIGIN=https://ваш-домен`, настроить HTTPS и маршрутизацию API на том же источнике. Go сам не раздаёт собранную страницу.

## Вложения

Установить ClamAV и актуальные базы сигнатур. `CLAMSCAN_PATH` задаёт путь к `clamscan`, иначе команда ищется через PATH. `UPLOAD_DIR` должен находиться на закрытом постоянном диске и быть доступен серверному пользователю. Без антивируса загрузки возвращают 503; остальные функции работают. 20.11.2026 ClamAV установлен локально, официальные main/daily/bytecode базы загружены и проверены; интеграционный тест реального сканирования/сохранения/скачивания PNG проходит. `CLAMAV_DATABASE_DIR` указывает каталог баз сигнатур; локально это закрытая от Git папка `backend/.local/clamav`. Одновременно допускаются две проверки, остальные загрузки получают понятную ошибку для повтора. Обновление баз: `freshclam --config-file=.local/freshclam.conf --stdout` из backend. При переносе на хостинг нужно обеспечить ClamAV, обновление его баз и постоянный закрытый диск для файлов.

## Проверки

Из `backend`:

```sh
go test -race ./...
go vet ./...
go run golang.org/x/vuln/cmd/govulncheck@latest ./...
```

Для интеграционных тестов использовать только отдельную локальную базу с префиксом `mgimo_`, предварительно заполненную командами `migrate` и `seed`. Эти проверки изменяют демонстрационные данные:

```sh
export TEST_DATABASE_URL="$DATABASE_URL"
export REQUEST_TEST_DATABASE_URL="$DATABASE_URL"
export MESSAGES_TEST_POSTGRES_URI="$DATABASE_URL"
export MESSAGES_TEST_MONGO_URI="$MONGODB_URI"
go test -race ./... -count=1
```

Без этих переменных интеграционные проверки пропускаются. Проверки заявок создают и удаляют собственные изолированные схемы; проверки сообщений создают и удаляют собственную тестовую MongoDB. Общая проверка API работает с демонстрационным набором и сохраняет изменения в нём. Не указывать рабочую базу продукта.

Проверки интерфейса из корня:

```sh
node --test frontend/api.test.mjs
npm run build
npm run lint
```

При запущенных Go API и Vite можно дополнительно проверить настоящий клиент:

```sh
export API_TEST_ORIGIN=http://localhost:5173
node --test frontend/api.integration.test.mjs
```

Для этого в окружении также должен быть `DEMO_PASSWORD`, установленный при seed.

## Облачное подключение

По решению владельца пока выполняется локальная проверка. После создания отдельных бесплатных проектов Supabase и MongoDB Atlas достаточно заменить серверные строки подключения и применить миграции к пустой базе. Бесплатность выбранной конфигурации и доступность из России нужно проверить перед созданием. Автоматического создания, оплаты или публикации облачных ресурсов нет. Актуальные особенности подключений описаны в [Supabase](https://supabase.com/docs/guides/database/connecting-to-postgres), ограничения бесплатного MongoDB — в [MongoDB Atlas](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/).
